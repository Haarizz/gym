C1

Receipt Vouchers bypass the general ledger entirely

CriticalMajor Feature

Issue summary. A Receipt Voucher created through the manual UI/API path (POST /api/receipt-vouchers) is saved and shown to the accountant as a ledger document, but it never creates a Journal Voucher and never updates any AccountHead.currentBalance. It matters because the Ledgers screen displays it next to genuinely posted entries with no visual distinction, so an accountant can mistake an unposted document for money that has actually hit the books.

AccountingManually entered receipts are invisible to the trial balance, Income Statement, and Balance Sheet, which read only journal_voucher_lines.
UserAccountant sees a “Receipt Voucher” row in Ledgers and reasonably assumes it is posted — it is not.
ReportingFinancial Reports / Analytics dashboards will under-report cash inflows recorded this way.
Data integrityTwo parallel “truths” exist: the ReceiptVoucher table and the JournalVoucher ledger, with no reconciliation between them.
ComplianceAn auditor reviewing account_heads balances would not find the cash reflected — a real books-don’t-match risk.

Current implementation. ReceiptVoucherController.createReceiptVoucher() (ReceiptVoucherController.java:43-47) calls ReceiptVoucherService.createReceiptVoucher() (ReceiptVoucherService.java:76-92), which only calls receiptVoucherRepository.save() and notificationService.notifyRoles() — no FinancialEventService call exists anywhere in that method. This is a documented design choice: LedgerTransactionService.java:26-29 states Receipt Vouchers are “informational” business documents, while member payments post through ReceiptService.settlePayment → FinancialEventService instead (a different code path, entity, and table). FinancialReportService.getIncomeStatement() (FinancialReportService.java:65-95) and FinancialAnalyticsService.getDashboard() confirm reports read exclusively from journal_voucher_lines joined to account_heads — so this gap is real, not a report bug.

Affected modules: Ledgers, Receipt Voucher, Financial Reports, Financial Analytics. Affected files: ReceiptVoucherController.java, ReceiptVoucherService.java, LedgerTransactionService.java, FinancialReportService.java, FinancialAnalyticsService.java.

Root cause. Two independent recording mechanisms were built for the same real-world event (money received): an automatic one driven by FinancialEventService for known system entities (Receipt, SaleTransaction, …), and a manual document-entry one (ReceiptVoucher) for anything an accountant types in directly. The second was never wired to the first.

Backend
  • On createReceiptVoucher(), when the voucher’s status is a postable state (e.g. "completed"/"Paid"), call a new FinancialEventService.onManualReceiptVoucherPosted(ReceiptVoucher) that debits Cash/Bank and credits the account implied by sourceCategory, mirroring the pattern already used by onMemberPaymentReceived.
  • Add the same idempotency guard already used elsewhere (JournalEntrySourceRepository.existsBySourceEntityTypeAndSourceEntityId("ReceiptVoucher", id)) so edits/re-saves cannot double-post.
  • Reject a status transition to a postable state when the accountant hasn’t picked a target account head.
Frontend
  • On the Receipt Voucher screen, make the “posted to ledger” state explicit (e.g. a status pill) instead of implying it via the Ledgers table row alone.
  • On the Ledgers screen, visually separate “business document, not yet posted” rows from “System Journal” rows (the backend already tags JV rows this way — see LedgerTransactionService.java:128).
Database
  • No new tables. Reuses journal_vouchers, journal_voucher_lines, journal_entry_sources, account_heads.
API
  • POST /api/receipt-vouchers and PATCH /{id}/status responses should include the linked journalVoucherId once posted, so the frontend can link out to the JV.
Validation
  • Require sourceCategory (mapped to a revenue/receivable account) before allowing a postable status.
  • Balance check: DR Cash/Bank must equal CR target account for every auto-generated entry (same invariant already enforced in FinancialEventService.createAndPost()).
Security
  • Not verified in the audit — no authorization gap was confirmed for this endpoint. Recommend restricting the postable-status transition to ACCOUNTANT/ADMIN roles as defensive practice, consistent with the roles already used in notificationService.notifyRoles() calls in this file.

C2

No database-level foreign keys anywhere in the financial schema

CriticalLarge

Issue summary. Every parent/child relationship in the financial schema — journal line → journal header, payment-voucher-bill → payment voucher, bank-statement-line → reconciliation, account head → parent account head — is stored as a bare Long column with no @ManyToOne/@JoinColumn mapping and therefore no foreign-key constraint in Postgres. It matters because nothing at the database layer prevents an orphaned line, a dangling reference, or a bad delete from silently corrupting the ledger.

AccountingA JV header could be deleted (see H3) while its lines remain, permanently unbalancing the ledger with no DB error.
UserNo user-visible symptom until a report is wrong — the failure mode is silent.
ReportingOrphaned journal_voucher_lines rows would be summed by FinancialReportService against a JV ID that no longer resolves to a status, skewing totals.
Data integrityConfirmed by grep across all 16 financial entities — none use @ManyToOne/@JoinColumn/@OneToMany, unlike non-financial entities such as Asset.java which do.
ComplianceReferential integrity is a baseline expectation for any auditable ledger.

Current implementation. JournalVoucherLine.java:14-15 declares @Column(name = "journal_voucher_id", nullable = false) private Long journalVoucherId; with no relationship annotation. The same pattern repeats for AccountHead.parentId (AccountHead.java:26-27), BankStatementLine.reconciliationId, PaymentVoucherBill.paymentVoucherId, and SupplierBillItem. Because spring.jpa.hibernate.ddl-auto=update (see C3), Hibernate only ever creates the column, never a constraint, for a plain Long field.

Affected modules: Ledgers, Journal Voucher, Payment Voucher, Bank Reconciliation, Chart of Accounts. Affected files: all 16 financial entity classes under com.company.project.entities.

Root cause. The financial entities were modelled with IDs-as-plain-columns rather than JPA object relationships — likely to keep queries simple and avoid N+1 fetch behavior — but this traded away the safety net a relational database is meant to provide.

Backend
  • Introduce explicit @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "...", foreignKey = @ForeignKey(name = "fk_...")) only where a true parent/child relationship exists (JV line → JV header; bill item → bill; statement line → reconciliation). Keep AccountHead.parentId as a nullable self-referencing FK with ON DELETE SET NULL.
  • Where introducing a JPA relationship would risk unwanted cascade/fetch behavior in already-shipped code, add the FK constraint directly via migration SQL (see C3) without changing the Java field type.
Frontend
  • No frontend change — this is purely a persistence-layer integrity fix.
Database
  • ALTER TABLE journal_voucher_lines ADD CONSTRAINT fk_jvl_header FOREIGN KEY (journal_voucher_id) REFERENCES journal_vouchers(id) ON DELETE RESTRICT;
  • Equivalent constraints for payment_voucher_bills, bank_statement_lines, supplier_bill_items, and a self-referencing FK on account_heads.parent_id.
  • Add supporting indexes on every FK column (see M1 — these same columns are also the ones being filtered on today).
API
  • No contract change. A delete that would now violate a constraint should surface as HTTP 409 rather than a raw 500 — ties into M2.
Validation
  • Before adding constraints, run an orphan-row audit query per table and resolve any pre-existing orphans (manually or via a cleanup script) so the migration doesn’t fail on deploy.
Security
  • Not verified in the audit — no security finding applies here; this is a data-integrity fix.

  • Integration: cascade/restrict behavior verified for each new FK.

C3

No schema migration tooling — Hibernate auto-DDL manages the production schema

CriticalMedium

Issue summary. There are no Flyway/Liquibase migration files anywhere in the repository. The schema is generated by spring.jpa.hibernate.ddl-auto=update. It matters because every future schema change (including C2’s foreign keys) currently has no reviewable, versioned, repeatable path to production — it depends on whatever Hibernate infers from entity annotations at boot time.

AccountingNo direct accounting impact today, but blocks safely applying C2’s integrity fixes.
UserNone directly visible, but an unreviewed auto-DDL change on deploy could alter a column type/nullability unexpectedly.
ReportingNone directly.
Data integrityddl-auto=update never removes columns/constraints and cannot add FK constraints for plain-Long fields — it can only grow the schema, never safely reconcile it.
ComplianceNo audit trail of schema changes over time — a real gap for any financial system expected to demonstrate change control.

Current implementation. application.properties:10 sets spring.jpa.hibernate.ddl-auto=update; application.properties:9 is the preceding comment header. A repository-wide search found no migration files under Gym-backend/src/main/resources or anywhere else.

Affected modules: entire backend/database layer. Affected files: application.properties; all entity classes indirectly.

Root cause. The project was likely bootstrapped for speed of iteration with auto-DDL and never transitioned to managed migrations as the schema (and its correctness requirements) grew.

Backend
  • Introduce Flyway (simplest fit for a straightforward Postgres/Spring Boot stack), add flyway-core dependency, and generate a baseline migration (V1__baseline.sql) from the current live schema.
  • Set spring.jpa.hibernate.ddl-auto=validate once Flyway is in place, so Hibernate only checks the schema matches the entities rather than mutating it.
Frontend
  • No change.
Database
  • All future changes (including C2) become versioned V__*.sql files applied in order and tracked in a flyway_schema_history table.
API
  • No change.
Validation
  • CI step that fails the build if a new entity field has no corresponding migration (process control, not code).
Security
  • Not verified in the audit. General practice: restrict who can run migrations in production to a controlled deploy pipeline.

H1

Account balance is mutated imperatively from three separate call sites

HighMedium

Issue summary. AccountHead.currentBalance is a stored, mutable value updated independently in JournalVoucherService.postJournalVoucher(), JournalVoucherService.reverseJournalVoucher(), and FinancialEventService.updateAccountBalance(). It matters because any new code path that posts a journal entry without going through one of these exact call sites (as already happened with Receipt Vouchers — see C1) silently desyncs the stored balance from the true sum of posted lines.

AccountingBalance sheet figures sourced from current_balance can drift from what journal_voucher_lines actually sums to.
UserAn accountant trusting the displayed running balance has no way to know it might be stale.
ReportingFinancialReportService/FinancialAnalyticsService already avoid this by recomputing from JV lines directly — but any screen reading current_balance directly is exposed.
Data integrityThree independent mutation points for one derived value is a correctness hazard by construction.
ComplianceA stored balance that can’t be proven to equal the sum of its postings is an auditability weakness.

Current implementation. JournalVoucherService.java:156-163 loops posted lines and calls financialEventService.updateAccountBalance() during postJournalVoucher(); JournalVoucherService.java:220-227 does the same during reverseJournalVoucher(); FinancialEventService.updateAccountBalance() itself (FinancialEventService.java:421-437) does current = current.add(debit).subtract(credit) and saves. It is also invoked from inside FinancialEventService.createAndPost() for every automatic entry.

Affected modules: Journal Voucher, Ledgers, Chart of Accounts. Affected files: JournalVoucherService.java, FinancialEventService.java, AccountHead.java.

Root cause. currentBalance was implemented as a cached/denormalized column for read performance, but no single choke point owns writing to it — every new poster of a journal entry must remember to call it.

Backend
  • Consolidate all balance mutation behind one method: FinancialEventService.updateAccountBalance() already exists as that single point for auto-entries — extend JournalVoucherService to call it exclusively (already does), and ensure C1’s new manual-posting path also routes through it (already planned).
  • Add a scheduled reconciliation job that recomputes SUM(debit-credit) from journal_voucher_lines per account and compares to current_balance, logging/alerting on drift — a safety net, not a replacement for point 1.
Frontend
  • No change required.
Database
  • No schema change; optional: add a nightly materialized check, not a live constraint (balance is inherently a running total).
API
  • No change.
Validation
  • Reconciliation job surfaces mismatches as a monitored metric, not a blocking validation.
Security
  • Not verified in the audit.

H2

Voucher-number generation is duplicated four times with weak concurrency safety

HighMedium

Issue summary. The same “read the last voucher number, increment, format” logic is independently implemented in four places, each guarded only by a JVM-level synchronized method — not a database-level lock or sequence. It matters because under concurrent requests (or any future multi-instance deployment), two requests can read the same “last” voucher number before either saves, producing duplicate numbers that only fail at save-time via the unique=true constraint, surfacing as an unhandled exception rather than a graceful retry.

AccountingA failed save due to a duplicate voucher number loses the user’s work with no automatic retry.
UserAccountant sees a generic error on an occasional concurrent submit and must re-enter the voucher.
ReportingNo direct effect once a voucher is successfully saved.
Data integritysynchronized only protects against concurrent threads inside one JVM instance — it does nothing across multiple app instances.
ComplianceVoucher numbering gaps/collisions undermine sequential-numbering expectations common in financial audit trails.

Current implementation. Identical logic appears at JournalVoucherService.java:42-55, FinancialEventService.java:454-467, PaymentVoucherService.java:37-50, and ReceiptVoucherService.java:30-43 — each queries findTopByVoucherNoStartingWithOrderByVoucherNoDesc(prefix), parses the numeric suffix, increments, and formats. Each method is declared private synchronized.

Affected modules: Journal Voucher, Payment Voucher, Receipt Voucher, auto-journaling engine. Affected files: JournalVoucherService.java, FinancialEventService.java, PaymentVoucherService.java, ReceiptVoucherService.java.

Root cause. The numbering logic was copy-pasted per voucher type instead of extracted into a shared, database-backed sequence generator.

Backend
  • Extract a single VoucherNumberService.next(String voucherType) backed by a dedicated Postgres sequence per prefix (or a single voucher_sequences(prefix, last_value) table updated via SELECT ... FOR UPDATE), removing all four duplicated methods.
  • On unique-constraint violation at save time, catch and retry once with a freshly generated number rather than surfacing a raw exception (belt-and-braces alongside the sequence fix).
Frontend
  • No change.
Database
  • New table or Postgres SEQUENCE per voucher prefix (JV, PV, RV) — a small, purpose-built migration once C3 is in place.
API
  • No contract change.
Validation
  • None beyond existing uniqueness.
Security
  • Not verified in the audit.

H3

Journal Vouchers can be permanently hard-deleted

HighSmall

Issue summary. JournalVoucherService.deleteJournalVoucher() performs a real repository.delete() on DRAFT or CANCELLED vouchers. It matters because once deleted, all record of that voucher having existed is gone beyond the generic createdBy/updatedBy audit columns on BaseEntity — there is no trace left for review.

AccountingNo POSTED voucher can be deleted (guarded), so ledger correctness itself is protected — this is about audit-trail completeness for drafts.
UserAn accountant who deletes a draft by mistake cannot recover it.
ReportingNo effect on POSTED-only reports.
Data integrityCombined with C2 (no FK), a delete could also orphan its lines if the guard were ever bypassed by a direct repository call.
ComplianceFinancial audit trails typically expect “nothing is truly deleted” for anything that ever existed as a financial document, even a draft.

Current implementation. JournalVoucherService.java:252-260: checks status is DRAFT or CANCELLED, then lineRepository.deleteByJournalVoucherId(id) followed by journalVoucherRepository.delete(jv) — a genuine hard delete of both header and lines.

Affected modules: Journal Voucher. Affected files: JournalVoucherService.java.

Root cause. No soft-delete convention exists anywhere in the financial entities (no deletedAt/isDeleted column on BaseEntity), so deletion defaults to a hard delete.

Backend
  • Add a soft-delete flag (e.g. deletedAt) to JournalVoucher/BaseEntity, change deleteJournalVoucher() to set it instead of calling repository.delete(), and filter it out of all list queries.
Frontend
  • No visible change — delete still appears to remove the voucher from view.
Database
  • New nullable deleted_at TIMESTAMP column on journal_vouchers (and optionally on other voucher tables for consistency).
API
  • No contract change.
Validation
  • Ensure every existing findAll...() query used by list/report endpoints excludes soft-deleted rows.
Security
  • Not verified in the audit.

M2

No centralized exception handling — generic RuntimeException everywhere

MediumMedium

Issue summary. Every “not found” or business-rule violation in JournalVoucherService.java (and its siblings) throws a plain RuntimeException with a message string. It matters because the frontend cannot reliably distinguish “voucher not found” (should be a 404) from “only DRAFT vouchers can be posted” (should be a 400/409) without parsing message text.

AccountingNo accounting impact.
UserErrors likely surface as a generic failure/toast rather than a specific, actionable message.
ReportingNo reporting impact.
Data integrityNo integrity impact — this is an API/UX consistency issue.
ComplianceNo compliance impact.

Current implementation. Confirmed at JournalVoucherService.java:78, 107, 138, 178, 239, 254 — every not-found case is throw new RuntimeException("... not found: " + id). The same pattern is used in ReceiptVoucherService.java and PaymentVoucherService.java. The audit did not find a @ControllerAdvice in the controllers reviewed, though an exhaustive project-wide search for one was not performed.

Affected modules: Journal Voucher, Payment Voucher, Receipt Voucher (and likely others following the same pattern). Affected files: JournalVoucherService.java, ReceiptVoucherService.java, PaymentVoucherService.java.

M4

MediumSmall

Issue summary. TaxComplianceService.getAll() flips any PENDING record past its due date to OVERDUE and persists it, inside what is otherwise a list-fetch operation.
