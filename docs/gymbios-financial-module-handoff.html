Architecture — the one fact that governs everything Context

FinancialEventService (Gym-backend/src/main/java/com/company/project/services/FinancialEventService.java) is the sole posting path for every module. No other service ever writes to JournalVoucherRepository directly for an automatic entry. It validates debit == credit before saving, posts inside one transaction, updates AccountHead.currentBalance, and guards idempotency via JournalEntrySource. Every new posting path added in future phases must go through it (an onXxx() handler) or through JournalVoucherService for manual entry — never around it.

This was not built from scratch this session — it already existed and was already mature. The original request asked for a full BillBull-style ERP financial architecture; a codebase survey found most of the core posting-engine requirements already satisfied, so work was scoped to the real, specific gaps instead of a rewrite.

Phase 1 — Deferred Revenue Recognition Done · compiled

Membership revenue was previously recognized 100% immediately on receipt, even for a 12-month membership paid upfront. Now: a Receipt with transactionType New/Renewal and a validFrom/validTill span longer than one calendar month gets its net (VAT-excluded) amount credited to Deferred Revenue (account 2300) instead of Membership Revenue, amortized evenly across monthly buckets, and recognized automatically as each month elapses. A plain 1-month payment is untouched — behaves exactly as before.

Built
  • DeferredRevenueScheduleService.qualifiesForDeferral() / createSchedule() — pure schedule bookkeeping, no dependency on the posting engine (avoids a dependency cycle)
  • FinancialEventService.onMemberPaymentReceived() branches to Deferred Revenue when applicable; new onDeferredRevenueRecognized() handler posts each monthly bucket
  • DeferredRevenueRecognitionScheduler — monthly cron (1st, 3am), mirrors the existing AssetDepreciationScheduler pattern
  • Report: GET /api/financial-reports/deferred-revenue
  • Bundled bug fixes: seeded the missing 5800 Depreciation Expense account (was hardcoded in code but never in the chart of accounts); gave Expense a paymentStatus field so onExpenseApproved() can credit Accounts Payable instead of always assuming instant cash

Phase 2 — Foundational Financial Infrastructure Done · compiled

Three independent pieces the later phases (and any serious accounting workflow) need underneath them: period locking, a general audit trail, and real dimension validation.

Built
  • Fiscal Year / Period locking — FiscalYear auto-creates 12 monthly FiscalPeriod rows on creation. FiscalPeriodService.assertPeriodOpen(date) is enforced at all 3 places a journal can become POSTED: FinancialEventService.createAndPost(), JournalVoucherService.postJournalVoucher(), reverseJournalVoucher(). Fails open by design — if no period is configured for a date, posting is allowed (with a log warning); only rejects when a period explicitly exists and is CLOSED/LOCKED. Current calendar year is seeded OPEN out of the box.
  • General audit trail — FinancialAuditLog (append-only: action/entity/voucher/module/performedBy/IP/summary) recorded on every JournalVoucher create/update/post/reverse/cancel/delete, and once inside createAndPost() so it covers every module's auto-postings as AUTO_POST rows in one hook. Not full before/after field diffs — this codebase has no entity-snapshotting infra to build that on, documented as a known limitation.
  • Cost center FK validation — on manual Journal Voucher lines and Expense entry, a supplied cost-center code must resolve against the existing CostCenter master table or the request is rejected. Blank/null still allowed (no forced tagging).
  • New endpoints: /api/fiscal-years (+ /{id}/close, /reopen), /api/fiscal-periods (+ /{id}/close, /lock, /reopen), /api/financial-audit-logs (filterable by entity/module/date)

Phase 3 — Missing Vouchers + Reports Done · compiled

Rounded out the voucher set and report suite using the existing posting engine as-is — no changes to FinancialEventService's core posting logic, only new handlers on top of it.

Built
  • Contra Voucher — cash ↔ bank transfers. onContraVoucherPosted(): DR to-account / CR from-account. Full DRAFT → POSTED/CANCELLED lifecycle.
  • Debit Note — supplier-side adjustments/returns. onDebitNoteIssued(): DR Accounts Payable, CR Purchase/COGS, CR GST Input Credit (reverses the input credit claimed on the original bill).

  • Endpoints: /api/contra-vouchers, /api/debit-notes, /api/credit-notes (each with /{id}/post, /{id}/cancel); /api/financial-reports/{cash-book,day-book,general-ledger,member-aging,supplier-aging}

Phase 4 — Tax Engine Expansion Done · compiled

Extended beyond the flat single-rate UAE VAT model on the purchase side (Expense, SupplierBill) — the side that already referenced a TaxCode by string. Membership/POS/add-on checkout flows were not retrofitted to per-transaction tax codes — see the deferred list below.

Built
  • TaxCode gained taxType (STANDARD/ZERO_RATED/EXEMPT/CGST/SGST/IGST) and secondaryTaxCode (pairs e.g. a CGST code with its SGST counterpart) — plus a CRUD service/controller, since none existed before (/api/tax-codes).
  • FinancialEventService.buildInputTaxLines() — resolves a TaxCode and, when it has a secondary, splits the input tax evenly across both accounts instead of one flat "GST Input Credit" line. Falls back to the original single-line behavior when no tax code is given — zero change for existing callers.
  • Wired into onExpenseApproved() (already had Expense.taxCode) and onSupplierBillConfirmed() (added SupplierBill.taxCode to match).
  • CompanyTaxDetails — single-row GST No / VAT No / TRN / legal name / address (/api/company-tax-details, GET/PUT upsert).
  • FinancialReportService.getTaxSummary() gained a tax_by_code breakdown — output/input amounts per configured TaxCode's own account(s), not just the flat 2100/2200 totals.
